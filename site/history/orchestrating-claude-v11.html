Lesson 1 · The big idea

Everything is one loop

An AI agent is a loop: plan a step, do it, check the result, and adjust. Orchestration, subagents, hooks and schedules are all ways to run this loop better. A sharper goal makes the check honest. A better plan makes each step smaller. A stricter check stops the loop from ending early.

Three roles keep this loop healthy, and you will see them on every page of this guide:

  • You set the goal, the bar for done, and the moments Claude must stop and ask.
  • The lead session (the orchestrator) holds the plan and makes the calls.
  • Helpers and gates do side work and run checks the lead can't skip.

Lesson 2 · Ten rules

Ten rules from the people who build it

These come from Boris Cherny, who created Claude Code, from Andrej Karpathy, from Anthropic's engineering team, and from practitioners who run agents every day. Each source line carries a tag showing how solid it is. Hover over a tag to see its source, and click P, S or R to open that source in a new tab. D tags are our own advice, so they only show the tooltip.

P their own words, or official docs S second-hand reports of a post R an independent research paper D advice built from the sources
  1. 01

    Keep the harness thin

    Let the model do the thinking. Every piece of scaffolding should name the failure it prevents, and go when a newer model no longer needs it.

    P Boris Cherny describes Claude Code as the thinnest possible wrapper over the model; better models absorb the scaffolding. Anthropic: start with the simplest thing that works.

  2. 02

    Make it prove its work

    A check Claude can run by itself is one of the biggest levers on quality.

    S Recaps of Boris Cherny's setup: a feedback loop improves results two to three times. P Anthropic's Agent SDK loop: gather context, act, verify, repeat.

  3. 03

    Give outcomes, not steps

    Say what done looks like and let Claude find the path.

    S Reports of Karpathy's notes: give success criteria and watch it go. P Anthropic: pitch prompts at the right altitude, then add rules only for failures you actually see.

  4. 04

    Treat context as a budget

    Load what the next step needs, not everything. Send heavy reading to helpers.

    S Karpathy endorsed "context engineering" over prompt engineering. P Anthropic: recall drops as the window fills; helpers return 1,000 to 2,000-token summaries.

  5. 05

    Let it search

    Fast grep-style search and a good map beat a retrieval pipeline for code.

    P Early Claude Code tried RAG with embeddings; plain agentic search outperformed it, by the team's own impressions rather than a benchmark.

  6. 06

    Plan before building

    Approve a plan of small, testable slices instead of approving every edit.

    S Boris Cherny starts most sessions in Plan mode; a good plan often lands in one shot. P Official best practices: explore, plan, code, commit.

  7. 07

    Keep maker and checker apart

    Reviewers get the work and the criteria, never the author's reasoning.

    P Best practices: an adversarial review subagent in a fresh context. Karpathy's llm-council has models review each other anonymously.

  8. 08

    Turn corrections into rules

    Capture each lesson, but keep CLAUDE.md short and push detail into skills and docs.

    S Boris Cherny: after a correction, tell Claude to update CLAUDE.md. P Best practices: cut any CLAUDE.md line whose removal wouldn't cause a mistake.

  9. 09

    Enforce with code

    Anything that must happen every time lives in a hook, CI or a permission rule, not only in prose.

    P A Stop hook exiting with code 2 blocks Claude from finishing. Anthropic's long-running harness forbade editing tests and kept state in JSON.

  10. 10

    Spend compute where it pays

    Fan out for wide reading and judgment calls; stay single-agent for tightly coupled edits.

    P Anthropic's multi-agent research system beat a single agent by 90.2% on its internal eval, at about 15 times the tokens of a chat. Karpathy, October 2025: this is the decade of agents, and they're weak at truly new code. S By December he was doing most of his own coding through agents.

Should you grill like Matt Pocock? Yes, with rules

  • Grill anything bigger than a one-line fix.
  • One question per message, with Claude's recommended answer and its cost. Pocock's own versions differ: one asks a question at a time, the newer one asks in rounds. Rounds get skimmed. His current skill words each question so a plain "yes" accepts the recommendation.

  • Write the spec in a fresh session, from the log.
  • Pocock's own caveat: no spec catches everything, so keep a QA loop that turns findings into new issues. P

Lesson 4 · Goals

Write a goal Claude can check

Claude is very good at doing. It needs you to define done. A goal without a test is a wish. Good goals have five parts:

  • OutcomeWhat is true when it's finished. Describe the result, not the activity.
  • Done when2 to 5 checks a command or a person can run. These are your success criteria.
  • ConstraintsWhat's off limits: files, packages, style, spending.
  • Stop and ask ifThe moments Claude must hand control back to you.
  • BudgetHow much effort: one session, how many helpers, which model.

Weak goal

"Make the reports page better."

Better how? Claude will guess, polish things you didn't ask for, and call it done when it runs out of ideas.

Strong goal

Outcome
Users can export the reports table to CSV.
Done when
1. Export downloads exactly the rows on screen. 2. npm test passes, with a new test for an empty report. 3. The file opens in Excel with the same columns as the table.
Constraints
Only change code in src/reports/; plans and notes go in docs/. No new packages.
Stop and ask if
A database change looks needed, or the same test fails twice.
Budget
One session, up to 3 helper agents.

Lesson 6 · Orchestration

  
One lead, many helpers

  
Orchestration means one Claude session acts as the lead. It holds the goal, the plan and the decisions. It hands narrow jobs to helper agents (subagents). Each helper starts with a clean memory, does one job, and sends back a short summary. The lead sees the conclusion, not the pile of reading behind it.


  

  
Why helpers keep the lead sharp

  
Every file Claude reads fills its context window, its working memory. When the window gets full, older turns are compressed and early details fade. Helpers do their reading in their own windows, so the lead stays light.


  

  

    

      
Send a helper when

      
    
        
  • The reading is wide (many files, many pages) and you only need the conclusion.
    • 
        
  • Jobs don't depend on each other, so they can run at the same time.
    • 
        
  • You want a judgment from someone who didn't do the work: review, critique.
    • 
        
  • A cheaper model can do it: search, summarize, list.
    • 
      

    

    

      
Do it in the lead when

      
    
        
  • It's a handful of steps and you know where to look.
    • 
        
  • The next step needs every detail, not a summary.
    • 
        
  • Writing the brief would take longer than doing the job.
    • 
        
  • Two helpers would edit the same files.
    • 
      

    

  


  
Brief a helper like a capable colleague who knows nothing yet. Its brief is the only context it gets. Say the goal, what's already ruled out, where to look, the scope, and the exact format to return. When you ask for a review, hand over the code and the criteria, not your conclusion. A reviewer that reads your conclusion tends to agree with it.

Scenarios to ask for every time

  
    
    
  • Happy path: normal use works.
    • 
    
  • Edge cases: empty, huge, odd characters, the first and last item.
    • 
    
  • Bad input: wrong type, missing field, no permission.
    • 
    
  • Regression: the thing that broke last time still works.
    • 
    
  • Failure: the network is down or a service times out, and the error is clear.
    • 
  


  

    Golden rule
    
The builder never grades its own homework. The check comes from a command, a hook, or a fresh agent.

  


  
The trust ladder

  
Each rung catches more, and costs more. Climb as high as the risk calls for: a typo fix needs rung 2; a change to login, payments or the database needs rungs 5 and 6.

  1. 1 · Claude says it's doneNothing on its own. A claim, not a check.
    2. 
    
  2. 2 · Claude shows the command and outputObvious failures, typos, broken builds.
    3. 
    
  3. 3 · A hook reruns the checksSkipped steps and checks that were never run.
    4. 
    
  4. 4 · A fresh agent reviews the changeThe builder's blind spots, weakened tests.
    5.

    6.

Lesson 10 · Guardrails

  
Guardrails that hold when nobody is watching

  
An instruction in a prompt is a request. Guardrails that hold live at the level of tools, the operating system and accounts, where the agent can't talk its way past them.


  

  
Facts to design around

  
    
    
  • Deny rules win. Claude Code checks deny, then ask, then allow; an allow can't override a deny, and deny rules hold in every mode. P
    • 
    
  • Auto mode is a convenience, not a wall. One independent stress test, using deliberately ambiguous tasks, found it missed 81% of risky actions, against the 17% Anthropic reports on real traffic. R
    • 
    
  • The sandbox only covers shell commands. File reads and edits, web fetches, MCP servers and hooks run outside it. Anthropic reports 84% fewer permission prompts with it on. Claude can also retry a failed command outside the sandbox; set allowUnsandboxedCommands: false to stop that. P
    • 
    
  • Managed settings beat repo settings, but only if you have a managed policy. With allowManagedPermissionRulesOnly on, repo allow, ask and deny rules are all ignored, so keep your deny rules in the managed file. Without a policy, run agents only in checkouts you trust. P
    • 
    
  • Headless runs trust the repo. claude -p without --bare runs the repo's hooks and MCP servers with no prompt. With --bare your own hooks don't run either, so put the checks in the CI job. P
    • 
    
  • Skills and tools are code you didn't write. A scan of 98,380 community skills confirmed 157 malicious ones, and poisoned MCP tool descriptions reached up to 72.8% attack success in tests. R
    • 
  


  

    

      
Prevent

      
    
        
  • Deny rules for secrets, enforced through managed settings
    • 
        
  • Sandbox on, with no unsandboxed retries; block reads of SSH and cloud keys with both sandbox and Read deny rules; a tiny network allowlist
    • 
        
  • No blanket shell allows when using auto mode
    • 
        
  • Drop one trifecta leg per session
    • 
        
  • Read and pin skills, plugins and MCP servers
    • 
        
  • Short-lived, narrowly scoped tokens
    • 
      

    

    

      
Detect

      
    
        
  • Log every tool call with a PreToolUse hook
    • 
        
  • Alert on denials and repeated blocks
    • 
        
  • Alert on edits to settings, CLAUDE.md, hooks and skills
    • 
        
  • Log network traffic leaving the sandbox
    • 
        
  • OpenTelemetry for sessions and cost
    • 
        
  • A StopFailure hook, so API errors and rate limits don't end a run silently
    • 
        
  • Logs the agent can't edit, with secrets redacted
    • 
      

    

    

      
Recover

      
    
        
  • Commit, or use a worktree, before long runs
    • 
        
  • Snapshot memory and rule files
    • 
        
  • Your approval, shown as a dry-run diff, for delete, send, publish, deploy and pay
    • 
        
  • A written kill switch: disable the task, stop the session, revoke its tokens, revert its branch
    • 
      

    

  


  
Top mistakes

  
    
    
  • Treating auto mode, or any "95% detection" filter, as a security boundary.
    • 
    
  • Skipping permission checks in a container that has your credentials mounted.
    • 
    
  • Blanket allows for the shell or script interpreters.
    • 
    
  • Assuming the sandbox covers file reads, hooks or MCP servers.
    • 
    
  • Letting a repo's own settings grant permissions, with no managed policy above them.
    • 
    
  • Installing community skills and MCP servers without reading them.
    • 
    
  • Loops with no cap on iterations, time or cost.
    • 
  







  
Lesson 11 · Running nonstop

  
Keep it running without you

  
There are three ways to make Claude work continuously. They differ in what wakes it up and whether your computer has to stay on.


  

  
Guardrails for anything that runs without you

  
    
    
  • A stop condition"Stop when every check passes, or after 10 runs." No open-ended loops.
    • 
    
  • A retry capAfter 2 failures with the same cause, stop and report. Don't try a sixth time.
    • 
    
  • Safe to repeatRunning twice must not send twice, charge twice, or create duplicates.
    • 
    
  • Short reportsOne line per run, and "no change" when nothing happened.
    • 
    
  • A home for resultsA file, a ticket, or a message. Not just the chat history.
    • 
    
  • Tight permissionsAllow only the tools it needs. Deleting, deploying, pushing to main and paying wait for you; pushing to its own branch is fine.
    • 
    
  • A cost ceilingPick the model and the interval on purpose. Every 5 minutes adds up fast.
    • 
    
  • Fresh context each passStart each run clean and read state from files, or compact on purpose. A context that runs for hours drifts.
    • 
  


  
Terminal, cloud, phone

  
Where each part of the work happens once you stop sitting at the screen.

Runs
Interactive sessions, plan mode, /loop, desktop scheduled tasks.

claude --cloud sessions, scheduled tasks, @claude in GitHub, auto-fix on PRs, Linear coding sessions.

      
You do
Pick the environment and network level, queue tasks, review PRs.

Works from your GitHub repo or an uploaded copy; you open the PR. Idle VMs get reclaimed, so state must live in git and files.

The Claude app or claude.ai/code; Remote Control into your laptop's session.

Triage, answer questions, nudge, start cloud tasks.

  • Cloud sessions keep running after you close the laptop, and count against your plan limits. P
    • 
    
  • Teleport pulls a cloud branch into your terminal, one way; after that the two copies drift apart. P
    • 
    
  • Auto-fix answers CI failures and review comments under your GitHub account, so it can set off comment-driven deploy bots. P
    • 
    
  • Use --max-budget-usd on headless runs; /usage is a local estimate and the Console is the real bill. P
    • 
    
  • A scheduled task can pause to ask you something, so check for paused runs as well as failed ones. Each run starts from a fresh clone and pushes to a claude/ branch, so keep its state in a ticket or PR comment, not in files. P

Lesson 12 · Linear and GitHub

  
From ticket to merged PR without watching

  
The shape that works: Linear holds intent and status, the agent works in a sandbox, GitHub holds the code and the gates, and you approve at the edges.


  

  

    

      
Who moves each status

      
    
        
  • Triage to Todo: you, or a triage rule.
    • 
        
  • Todo to In Progress: the agent, when you delegate.
    • 
        
  • In Progress to In Review: your team's GitHub automation (check its settings), not the agent.
    • 
        
  • In Review to Done: merging a PR that says "Fixes ID", after your approval.
    • 
        
  • Anything to awaiting input: the agent, with a question instead of a guess.
    • 
      

    

    

      
The gate at each step

      
    
        
  • Intake: only people with write access can trigger the agent; bots allowed by name.
    • 
        
  • Agent run: its own branch prefix and pushes only there, a read-only token otherwise, only the tools it needs, no secrets, a network allowlist.
    • 
        
  • Draft PR: the agent can't approve or merge.
    • 
        
  • Checks: required checks in a ruleset; a person approves workflow runs on agent PRs.
    • 
        
  • Review: AI comments only; a person approves, and not the one who asked.
    • 
        
  • Merge and deploy: merge queue reruns checks; environment reviewers, no admin bypass.
    • 
      

    

  


  
Things worth knowing

  
    
    
  • Set up the Claude GitHub Action with /install-github-app; trigger it with @claude, a label or assignment. Bots are blocked by default, but any bot you allow-list skips the permission check, so never allow every bot on a public repo. P
    • 
    
  • On PR runs the action restores .claude/, CLAUDE.md and .mcp.json from the base branch, but package scripts still come from the PR. P
    • 
    
  • pull_request_target runs with secrets: never check out and run PR code there. Pass issue and PR text through env:, and pin actions to a full commit SHA. P
    • 
    
  • CODEOWNERS is read from the base branch, so a PR can't add its own owners. A merge queue needs CI to listen for merge_group. P
    • 
    
  • In Linear you stay the assignee and the agent is a delegate. Put repo and gate rules in Linear's agent guidance once, not in every ticket; it's advice to the agent, not a gate. P
    • 
    
  • Link work with "Fixes ID" in the PR; commit magic words can close an issue without any review. P
    • 
    
  • Field report: small, specific tickets merged cleanly, while a vague "make it snappier" ticket got a cosmetic fix that missed the real cause. S
    • 
  


  

    Protect the gates
    
An agent that can edit CI, hooks or gate config can switch off its own checks. Put those files behind path rules and code-owner review.

  







  
Lesson 13 · Growing

  
Plan, measure, improve

  
An agent setup gets better only if each run teaches the next one. That takes a short retro after real work, and a few numbers to tell you whether it's working.


  

  

    

      
Signs you are planning

      
    
        
  • A plan file exists before the first edit.
    • 
        
  • Every slice names the test that proves it.
    • 
        
  • Risks and the way to undo each change are written down.
    • 
        
  • Big decisions are recorded with the reason (an ADR or a short note).
    • 
        
  • When reality changes, the plan changes, and the change is noted.
    • 
      

    

    

      
Signs you are growing

      
    
        
  • Verify passes on the first try more often.
    • 
        
  • You step in to correct Claude less often.
    • 
        
  • Fewer bugs turn up after shipping.
    • 
        
  • Your CLAUDE.md and skills change a little every week, and stay short.
    • 
        
  • Tasks you used to watch now run on /loop or /schedule.

Lesson 14 · Prompt library

  
Prompts that make Claude work on its own

  
Copy one, fill in the parts in angle brackets, and paste it into Claude. The goal prompt from Lesson 4 is the main one; these cover the rest of the loop.


  

    
    
    
    
    
    
    
    
  


  

    
Claude researches on its own, merges what it found, recommends, and has its pick challenged before you see it.


Research question: <the question>
It feeds this decision: <what I will decide with the answer>

1. Explore. Start 3 read-only helper agents in parallel, one per angle:
   a) <angle 1, e.g. official docs>
   b) <angle 2, e.g. our codebase>
   c) <angle 3, e.g. known problems and bug reports>
   Each returns up to 10 findings, each with a source (file:line or link)
   and a confidence: high, medium or low.
2. Synthesize. Merge them into one brief: what the sources agree on,
   where they conflict, and what is still unknown. Every claim keeps its source.
3. Recommend. Give 2 or 3 options with trade-offs, then your pick and why.
4. Advisory review. Send only the brief, not your reasoning, to a fresh
   reviewer agent. Tell it to argue against your pick and name its
   3 strongest objections.
5. Answer each objection: change the pick, or explain why it stands.
6. Save the final brief to docs/research/<topic>.md and show me
   a 5-line summary.

  


  

    
Paste before Claude wraps up. It turns "done" into a receipt you can check.


Before you tell me this is done:

1. List every success criterion from the goal.
2. For each one, run the check. Show the command and the last lines
   of its output.
3. Mark each PASS, FAIL or NOT RUN (say why). NOT RUN is not PASS.
4. Also test these scenarios:
   - Happy path: <normal use>
   - Edge case: <empty, huge or unusual input>
   - Bad input: <wrong type, missing field>
   - Regression: <the thing that broke last time>
5. Start a fresh reviewer agent. Give it only the diff and the criteria,
   not your summary. Fix or answer each finding.
6. Then write the summary: what changed, what passed, what is not done.

  


  

    
The shape of a good brief for any helper agent. Use it yourself, or tell the lead to brief helpers this way.


Goal: <what you need back, and the decision it feeds>
Already ruled out: <what has been checked, so it is not redone>
Look here: <files, folders, URLs>
Scope: read-only. Do not edit anything. Stop after <N> files or sources.
Return: up to 10 findings, each with a file:line or link and a
confidence (high, medium, low). Say plainly what you could not find.

  


  

    
Repeats inside this session while it stays open. Leave out "30m" to let Claude choose its own pace.

Sets up a cloud scheduled task that runs on a timetable, even with your computer off. It can still pause to ask you something. Describe the timing in plain words.

<the task, e.g. read yesterday's failed CI runs and group them by cause>.

Two minutes after a real task. This is the Learn phase, and how the setup grows.


Retro on this task. Be specific and short.

1. Where did we spend more turns than we should have, and why?
2. What did I have to correct you on?
3. Which check caught a real problem? Which check was missing?
4. Did any helper agent waste effort or come back empty?
   What was wrong with its brief?
5. Propose up to 3 changes that would make the next run better.
   Each is a CLAUDE.md rule, a skill, a hook or a test.
   Show the exact text or code.
Don't apply anything until I say yes.

  


  

    
Discovery before any plan: Claude interviews you until the design is settled, and writes nothing else.


Grill me about <idea>. The goal is shared understanding before any plan or spec.
Rules:
- One question per message. Give your recommended answer and what it costs.
- Never ask me something you can find in the code, docs or data.
  Look it up and tell me what you found.
- Walk the design tree: settle prerequisite questions before the ones
  that depend on them.
- Keep a decision log in docs/discovery/<topic>.md: question, answer, reason.
- Cover: who struggles and when, the outcome metric, the time budget,
  no-gos, rabbit holes, failure cases, open questions.
- Stop when nothing is open or after <N> questions, then summarize
  the decisions for me to confirm.
Do not write a plan, spec or code in this session.

Lesson 15 · When it goes wrong

  
Common failures and their fixes

  
Almost every problem with autonomous agents traces back to a missing goal, a missing check, or too much in one context.

  

    

      
What you seeLikely causeFix

      
        
Wanders, gold-platesThe goal has no "done when".Add checkable criteria and a stop rule.

        
"Done!" but brokenThe builder graded its own work.Require command output; add a hook or a fresh verifier.

        
Forgets early detailsThe lead's context filled up with raw reading.Send reading to helpers; keep the plan in a file.

        
Same error, fifth tryNo retry cap.Stop after 2 failures with the same cause; ask a fresh agent for a second opinion.

        
Reviewer always agreesIt read your reasoning first.Give it only the code and criteria; ask it to argue against.

        
Huge token billHelpers spawned for small jobs, or a loop that runs too often.Delegate only wide reading, parallel work or fresh judgment; slow the loop.

        
Agents overwrite each otherTwo writers on the same files.One writer per set of files; use worktrees.

        
Overnight run did something riskyToo much permission.Allow-list its tools; keep irreversible actions behind your approval.

        
Auto mode let something throughIt was treated as a security boundary.Rely on deny rules, the sandbox and managed settings; auto mode is a convenience.

        
The loop ran all nightNo cap on iterations, time or cost.Cap all three. One uncapped loop ran 6,239 iterations.

        
Tests pass, spec still brokenThe loop optimized for the tests it had.Keep a fresh-eyes review even when everything is green.

        
Agent turned off its own checksIt could edit CI, hook or gate files.Path rules and code-owner review on those files.

        
CI ran the repo's hooks unexpectedlyclaude -p without --bare.Use --bare (then run your checks as CI steps), or run only on a trusted checkout.

        
Run ended with no receiptAn API error or rate limit; the Stop gate never ran.Add a StopFailure hook that records the failure and notifies you.

Lesson 17 · What the evidence says

  
Proven orchestration, by the evidence

  
This lesson counts only measured results: peer-reviewed or well-cited studies, research reports, and engineering write-ups from large teams that publish numbers. No YouTube and no product marketing. When a company reports on its own product, the playbook marks it as vendor-reported.


  

  
Six findings that hold up

  
    
    
  1. 01
    One writer by default
    Fan out only for parallel, read-heavy work. Steps that depend on each other go worse with more agents.
    Anthropic's 2026 guidance: start with one agent and split by context boundary, not job title. P Thoughtworks puts coding-agent swarms on caution. P
    2. 
    
  2. 02
    Wrap the model in a scripted pipeline
    At scale, teams script targeting, checks and merging, and call the model only for the edit.
    Airbnb migrated about 3,500 test files: 75% in 4 hours, 97% in four days, about 6 weeks against an estimated 1.5 engineer-years. P Google: 74% of 595 migration changes were model-generated, then validated and approved by code owners. R Spotify has merged 1,500+ agent PRs behind build and test checks and a stop hook. P
    3. 
    
  3. 03
    External checks beat self-critique
    Tests, builds and a verifier step raise reliability; asking a model to re-check itself without a signal doesn't.
    Adding a verifier fixed 15.6% more multi-agent runs across 1,600+ traces. R Self-correction without outside feedback lowered reasoning accuracy. R Meta kept only generated tests that built, passed and added coverage; engineers accepted 73% of those. R
    4. 
    
  4. 04
    Design the tools, keep the shape simple
    A better agent-computer interface or a fixed pipeline often beats a complex agent.
    SWE-agent's purpose-built file tools added 10.7 points over a raw shell. R A fixed localize-repair-validate pipeline solved 32% of SWE-bench Lite at about $0.70 per issue. R A simple retry baseline scored 93.2% for $2.45 where a complex agent scored 88.0% for $134.50. R
    5. 
    
  5. 05
    Measure reliability and cost
    One good run flatters an agent; repeated runs and full test suites tell the truth.
    GPT-4o passed about 61% of tau-bench tasks once, but under 25% eight times in a row. R 7.8% of SWE-bench patches marked resolved fail the full test suite. R
    6. 
    
  6. 06
    Human review is the bottleneck
    Speed-ups are mostly self-reported, and people overestimate them.
    In METR's randomized trial, experienced developers were 19% slower with early-2025 AI tools while believing they were 20% faster. R DORA 2025: 90% use AI; it goes with higher throughput and still with more instability. P
    7. 
  


  
Pick the shape by the task

  

    

      
Task shapeShape that held upEvidence

      
        
Many independent, read-heavy partsA lead with read-only helpers and a central coordinatorAnthropic's research system won by 90.2% on breadth-first research P

        
Steps with shared state (most feature work)One agent writes; helpers only read or reviewMulti-agent lost 39–70% on sequential planning R; Cognition keeps writes single-threaded P

        
A large mechanical change across many filesA scripted pipeline; the model edits; checks gate every fileAirbnb, Google, Spotify; Uber's batch AI migration failed P

        
Searching for a better solution with a machine scoreGenerate, score, keep the bestDeepMind's AlphaEvolve found a scheduling rule that recovers 0.7% of Google's fleet compute P

        
A judgment call with no testSample several answers and vote, or ask a fresh critic; a person decidesSelf-consistency added 17.9 points on a math benchmark R

      
    

  


  
Where reputable sources still disagree

  
    
    
  • Multiple agents. Anthropic's 2025 research system and Andrew Ng favor them P; Cognition, Thoughtworks, the MAST study and Google's study are skeptical for coding. Task shape explains most of the split.
    • 
    
  • Planning. Andrew Ng calls planning the least predictable pattern; Chip Huyen treats it as core and validates plans before running them. P
    • 
    
  • Humans in the loop. OpenAI's Codex team moved most review agent-to-agent P; Microsoft's Magentic-UI study raised success from 30.3% to 51.9% with human co-planning (a simulated user). R
    • 
  


  

    
What this means for your harness D

    
    
      
  • One writing agent by default; helpers read, search or review.
    • 
      
  • For big mechanical changes, script the pipeline and gate every file. Budget for the long tail.
    • 
      
  • Verification first. Don't count on self-critique without a test or checker.
    • 
      
  • Track all-runs pass rate and cost per task, not single wins.
    • 
      
  • Size agent output to what people can actually review.
    • 
    

  

  
Gathered by four research agents on 24 October 2026, mostly from paper abstracts, paper text and engineering posts. Spot-check a number against its source before quoting it. Biggest gap: no peer-reviewed, cost-matched comparison of orchestration setups on real coding work with current models, and almost no published defect or revert rates from industry.

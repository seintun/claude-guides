The guide is a separate folder of advice; call it GUIDE. The work happens in the current project, never in GUIDE.

1. Find GUIDE: run `git -C "${CLAUDE_SKILL_DIR}" rev-parse --show-toplevel`. If that folder holds `skills/guide/SKILL.md` and `tools/section.py`, GUIDE is that clone. Any other folder is the project the skill was copied into, never GUIDE, even if it has an `ENTRY.md`. Otherwise (the skill was copied in by `npx skills add`, or another agent fetched this file) GUIDE is `https://raw.githubusercontent.com/<owner>/<repo>/<branch>`, with `<branch>` from the link if it names one (else `main`) and `<owner>/<repo>` taken from the repository link the user gave, else from the `CLAUDE_GUIDES_REPO` environment variable, else `seintun/claude-guides`. That is remote mode: read files with `curl -fsSL GUIDE/<path>`, or WebFetch asking for the file's full text (it may summarise; prefer curl).
2. Read `GUIDE/ENTRY.md`. It is the only guide file you read in full.
3. Match the request to one row of its scenario router, or to a phase if no row fits. The request: $ARGUMENTS
   If the request is empty or fits no row, ask the user one question that picks a row.
4. Load that row's sections in one call: `python3 -I GUIDE/tools/section.py <ids>`. In remote mode, fetch the row's bundle `GUIDE/routes/row-<n>.md` (or `routes/phase-<n>.md`) instead; for a single id, `GUIDE/sections/<id>.md` (`cs:3` is `sections/cs-3.md`). Open the row's runbook in `GUIDE/wiki/` only if you need its steps or checklist. Never read `GUIDE/playbook/agent-harness-playbook.md` whole.
5. **Check freshness.** Read `playbook_version` and `playbook_updated` from `GUIDE/guide-index.json` without reading the whole file: in a clone, `python3 -I -c "import json,sys;d=json.load(open(sys.argv[1]));print(d['playbook_version'],d['playbook_updated'])" GUIDE/guide-index.json`; in remote mode, run `curl -fsSL GUIDE/guide-index.json`, then pass its output to `python3 -I -c "import json,sys;d=json.load(sys.stdin);print(d['playbook_version'],d['playbook_updated'])"`. Always run this step, even for a quick question.
   - In a clone, compare with `main`. Get owner and repo from `git -C GUIDE remote get-url origin` (reduce the SSH or HTTPS GitHub URL to `<owner>/<repo>`; if there is no GitHub remote, skip the comparison and say freshness was not checked), then read `https://raw.githubusercontent.com/<owner>/<repo>/main/guide-index.json` the remote-mode way. If `main`'s version or date is newer, say "your clone is behind main; run `git pull`" and do not answer from the stale copy without saying so. If the fetch fails, say freshness was not checked.
   - Only if `GUIDE/news/README.md` exists (it defines the digest format): if the newest digest is dated after `playbook_updated` and lists "adopt" items that name the sections you chose, list them as "newer, not yet folded in", with their links and grades. If the folder is missing, skip this check silently.
   - If `playbook_updated` is more than 45 days old (a design choice [D], not a playbook rule), say the guide may lag current practice; if `GUIDE/skills/refresh/SKILL.md` exists, suggest `/refresh scan`, otherwise suggest pulling the latest guide.
6. Answer for this project. Start with one line in exactly this form, filled in: `Guide: playbook <version>, <date> · <freshness result>` (the result is "current with main", "your clone is behind main; run `git pull`", or "freshness not checked"). Then:
   - the row you chose, in one line, and the runner-up if two rows fit;
   - what to do now, as numbered steps drawn from the sections, citing them as §9.5, Template F, and so on, each ending with its evidence grade in brackets, [P], [S], [R] or [D] (P primary, S second-hand, R research, D design advice), taken from the section text. Where a P or R claim and an S claim cover the same step, give the P or R one. Never give an item that playbook §19.5 marks as superseded, or any file under `GUIDE/archive/`, as current advice; open the archive only if the user asks about history;
   - the row's template filled in for this project, when the row names one;
   - the output the row asks for, and the checks that prove it.
   If the row is marked thin, say what the playbook lacks instead of filling the gap from memory.
7. **Log it when real work follows.** If the user goes ahead with the work (not for a quick question), append one dated line to the current project's `docs/decisions.md`: the request, the row and sections chosen, and each decision made, with its reason. Commit it with the work. Raw notes and helper output go to an ignored folder, never the log. Records belong on disk, not only in chat, because recall fades as context fills and sessions forget (Law 4, §8, §14; see `GUIDE/wiki/records.md`).
